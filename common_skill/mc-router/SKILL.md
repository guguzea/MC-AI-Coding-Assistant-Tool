# mc-router — 流程选型路由

一句话目标：把用户说的「我想做 X」翻译成**下一个具体动作**，并给出核实过存在的入口名。

## 第 1 步 · 归类情况

| 情况 | 去处 |
| --- | --- |
| 新内容 / 新机制，需求未定型 | 先 mc-grill 对齐，对齐完回到本路由选开发流程 |
| 明确的开发或修复（方块 / 实体 / GUI / 网络 / 世界生成 / 配置…） | 对应开发工作流（名字在第 2 步的实况名单里核） |
| 报错 / 崩溃 / 日志 | 崩溃分诊类工作流 |
| 写完代码问「够不够」 | 构建与静态校验面（validate_project / audit_resources 一类）→ 游玩自测（需三通道授权，未授权不得代跑，按未测报） |
| 移植 / 升版 / 汉化 / 反编译研究 / 发布 | 对应专项工作流；发布上传必须人工执行，agent 只给清单 |

归不进 → 用 mc-grill 的提问法先问一个问题：「这一步做完，你想能做什么？」问完回来再归类。

## 第 2 步 · 查实况名单（禁止凭记忆报名）

- MCP 在：`list_knowledge_resources` 就是实况名单——`workflow-` 前缀条目 = 工作流模板全量（带标题行），`skill-` 前缀 = 编排技能。核到名字后再 `get_workflow_template` 取正文；传名单外的名字会被 schema 枚举直接拒（校验错误的期望值面也含全量名单，可作兜底来源）。
- MCP 不在：读平台包的 skills 索引（`activate_platform_pack session` 返回，或宿主技能目录的安装件）。
- 名单里核不到的名字，一律不当存在；说「本面没有这条现成流程」，不编。

## 第 3 步 · 推荐格式（三行制）

- **主推荐**：<模板/技能/工具名> + 一句为什么（依据用户工程实况，「业界惯例」不算理由）
- **备选**：<名> + 一句为什么没当主选
- **入口**：可直接执行的写法（如 `get_workflow_template --name=...` 或 `/mc-grill`）

推荐必须落到「现在就能做的一步」；落不下去就明说没有现成流程，给手工方案让人拍板，禁止硬凑。

## 边界

- 路由只给**下一跳**，不接管流程执行——落地到去处后按那个流程走，不再回炉推荐。
- 用户已选定流程、流程缺某一步 → 不回路由，把缺口标「本面没有」交给用户决定。
- 同一段对话只路由一次；中途情况实质变了才重入。
